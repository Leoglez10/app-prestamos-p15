# Skill: release

## Activation Contract

Use when the user asks to publish a release, create a tag, bump the version, or verify a release for this Tauri app. Also use when the user pushed code and wants it released, or asks "how do I make sure the release works".

## Hard Rules

- NEVER create tags manually with `git tag`. ALWAYS use `scripts/publish-release.sh` from the app subdirectory.
- NEVER edit version files by hand. The script syncs all 4 files atomically with rollback on failure.
- Before releasing, the skill MUST commit and push any pending functional work first (see Pre-Release Step). Only AFTER `HEAD == origin/main` is the tree ready for the release script.
- Version format MUST be `X.Y.Z` (semver). No `v` prefix in the version argument to the script.
- Tags use `v` prefix: `v0.1.4`. The script adds it automatically.
- CI runs on a push to `main`, on `tags: v*`, and manually. **A push to `main` that carries `feat:` or `fix:` commits RELEASES BY ITSELF**: it bumps the patch version, stamps the docs, commits `release: vX.Y.Z` and publishes the signed Release. A push with only `docs:`/`chore:`/`ci:`/`style:`/`test:` publishes nothing. Pushing functional work to `main` IS releasing it — there is no separate confirmation step.
- Wait for CI to complete (~7-8 min). A green run does NOT guarantee the release exists; verify assets explicitly.
- Every release MUST ship updated user-facing docs. `scripts/publish-release.sh` calls `scripts/stamp-release-docs.sh`, which stamps the version into `README.md`, `CHANGELOG.md` and `docs/MANUAL_PERSONAL.md`. NEVER edit those version numbers by hand.
- The stamper only handles version numbers and a generated `feat:`/`fix:` CHANGELOG section. Whatever the release CHANGES for the staff (a new screen, a moved button, a different flow) MUST be written into `README.md` and `docs/MANUAL_PERSONAL.md` BEFORE the release, in the Docs Step below. The manual PDF the CI attaches to the tag is built from that Markdown, so anything missing there is missing from the PDF the staff downloads.
- README and the manual are written for professors and staff, never for developers: plain language, concrete steps, no technical jargon. The README's "¿Eres una IA leyendo este repositorio?" block states this contract — follow it when writing docs for a release.
- Conventional Commits only for the functional commit (feat:/fix:/refactor:/chore:). The release commit uses `release: vX.Y.Z` and is generated by the script, not by hand.

## Decision Gates

| Situation | Action |
|-----------|--------|
| Working tree dirty (untracked/staged/unstaged) | Run the Pre-Release Step: ask for a Conventional Commits message, commit all, push to main. Then continue with release. |
| Working tree clean but `HEAD != origin/main` | Run `git push` (no commit needed). If push rejected (remote ahead), pull --rebase first. Then continue. |
| Working tree clean and `HEAD == origin/main` | Skip Pre-Release Step. Go straight to release. |
| Release changes something the staff sees (screen, button, flow, new feature) | Run the Docs Step: update `README.md` and `docs/MANUAL_PERSONAL.md` in plain language, commit with the functional work. |
| Release is internal only (refactor, deps, CI) | Skip the Docs Step. The stamper still syncs version numbers and the CHANGELOG. |
| README/CHANGELOG/manual version numbers look stale | Do nothing by hand; the next release stamps them. To fix without a release: `bash scripts/stamp-release-docs.sh <version>` and commit as `docs:`. |
| User wants release, no version specified | Ask: patch (0.1.X+1), minor (0.X+1.0), or major (X+1.0.0)? Default: patch |
| User gives exact version (e.g. "0.2.0") | Use that version directly |
| User wants release of current version (no bump) | Run `bash scripts/publish-release.sh` with no version arg |
| Tag already exists for target version | STOP. Bump to a higher version. Never force-overwrite tags |
| You need to CONTROL the version number | Use `scripts/publish-release.sh <version>` manually. A plain push to `main` always cuts a PATCH bump |
| You want to know what a push would release, without publishing | `bash scripts/release-gate.sh --range <tag>..HEAD` prints the decision and writes nothing |
| CI failed | Read `gh run view <id> --log-failed`, fix, commit, push, re-tag with next version |
| Release exists but no assets | CI didn't upload. Re-trigger by deleting tag+release and re-running with next patch |

## Pre-Release Step (commit + push functional work)

Run this ONLY when the working tree is dirty OR `HEAD != origin/main`. Skip when already clean and pushed.

1. **Inspect**: `git status --porcelain` and `git log --oneline origin/main..HEAD` (unpushed commits).
2. **Classify**: list changed files and unpushed commits for the user.
3. **Ask for commit message** (only if there are uncommitted changes): request a Conventional Commits message. Offer to auto-suggest based on diff (e.g. `feat: add logout button to Kiosk` if new files in src/pages/Kiosk.tsx). NEVER use `release:` prefix for functional commits.
4. **Stage and commit**: `git add -A` then `git commit -m "<message>"`. If user gave multiple concerns, split into multiple commits with their own messages.
5. **Push**: `git push origin main`. If rejected because remote is ahead, run `git pull --rebase origin main` first, resolve if needed, then push.
6. **Verify gate**: `git status --porcelain` (must be empty) and `git rev-parse HEAD` must equal `git rev-parse origin/main`.
7. **Continue** to Execution Steps below.

## Docs Step (README + staff manual)

Run BEFORE the release script, together with the Pre-Release Step, whenever the release changes anything a professor or staff member would notice.

1. **Read the diff** of the functional commits and list what changed for the USER, not for the code.
2. **Update `docs/MANUAL_PERSONAL.md`** — the operational manual. New screen or flow → the matching chapter. Changed behavior → fix the steps. This file becomes the PDF attached to the release.
3. **Update `README.md`** — only the sections a user reads: *Vista rápida*, *Cómo usar la app paso a paso*, *Dudas frecuentes*, *Documentación relacionada*.
4. **Write the CHANGELOG entry** when the generated `feat:`/`fix:` bullets would not read well to a human. A hand-written `## [X.Y.Z]` section always wins: the stamper detects it and leaves it alone.
5. **Language contract**: plain Spanish for professors and staff, concrete steps, no jargon. Never version numbers by hand — the stamper owns those.
6. **Commit** the docs with the functional work (`docs:` or inside the `feat:`/`fix:` commit), then push. Continue to Execution Steps.

## Execution Steps

1. **Verify state**: `git status --porcelain` (must be empty) and `git rev-parse HEAD` must equal `git rev-parse origin/main`. If not, run the Pre-Release Step first.
2. **Confirm version**: Determine target version with user if not specified.
3. **Publish**: Run `bash scripts/publish-release.sh <version>` from the app subdirectory (`app-prestamos-p15/app-prestamos-p15/`).
   - Script bumps 4 version files, stamps README/CHANGELOG/manual, commits "release: vX.Y.Z", pushes to main, creates tag, pushes tag.
   - Without a version argument it stamps the docs too, and commits them as `docs: actualiza los documentos a vX.Y.Z` before tagging.
   - On failure BEFORE the release commit, it reverts the version files. After the commit it does NOT pretend to revert: the commit is already the truth, so it prints the exact command needed to finish (push the commit, or create and push the tag).
4. **Monitor CI**: `gh run list --limit 3` then `gh run watch <id>` or poll `gh run view <id> --json status,conclusion`.
5. **Verify tag**: `git tag -l "v*"` locally and `git ls-remote --tags origin` on remote.
6. **Verify release**: `gh release view v<version> --json assets,isDraft,isPrerelease`. Confirm `isDraft: false`, `isPrerelease: false`, and assets list includes `.exe`, `.msi`, their `.sig`, `latest.json` and `manual-personal-app-prestamos-p15.pdf`.
7. **Report**: Return release URL, asset names, and file sizes to the user.

## Output Contract

Return:
- Release version and tag name
- CI run status (success/failure + duration)
- Release URL from GitHub
- Asset list with names and sizes
- Any warnings or follow-up actions needed
